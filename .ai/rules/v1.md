# V1

## Jangan hapus currentAccessToken tanpa guard; jangan terbitkan token yatim
SPA ini murni cookie-based Sanctum; frontend tidak pernah mengirim header Authorization. Jangan terbitkan Bearer token di login, dan saat menghapus currentAccessToken selalu guard dengan method_exists karena sesi cookie memakai TransientToken yang tidak punya delete().

## Daftarkan selisih di menu penerima email
Notifikasi selisih qty memakai document_type='selisih' + trigger='selisih_qty'. Pastikan kedua nilai ini ada di options() dan aturan validasi in:... di EmailRecipientController agar muncul di menu penerima email. Frontend onezentra-web/src/app/email-recipients/page.tsx punya docTypeLabel/triggerLabel yang harus memuat 'selisih' dan 'selisih_qty'.

## Standarisasi Tumpukan di validasi SJ
Integrasi Standarisasi Tumpukan ke alur validasi SJ: (1) show() melampirkan atribut dinamis `standarisasi` ke tiap item (lookup terakhir by **`npn_id`** — tabel kini ber-`npn_id` FK, kolom BOSnet denormal sudah dihapus; jangan pakai BOSnetszProductId/szBarcode); (2) scanItem menerima opsional tier + tinggi_tumpukan → upsert record standarisasi_tumpukan status `pending`, total_tier_tinggi=tier*tinggi, requested_by=user aktual. Frontend validasi-sj menampilkan reminder bila standarisasi ada, dan input wajib tier/tinggi bila belum ada (Simpan dikunci sampai lengkap).

## Jenis kendaraan & kubikasi derived di rencana kirim
rencana_kirim memakai kolom jenis_kendaraan (teks tipe kendaraan, tanpa perhitungan kapasitas). Kubikasi muatan TIDAK disimpan di DB: dihitung derived per request = jumlah × npn.decVolume × npn.SAPdecUom ÷ 1.000.000 m³ (decVolume = cm³/pcs, SAPdecUom = pcs/satuan). Dilampirkan sbg `kubikasi` per item dan `total_kubikasi` di index/show/store/update. Frontend menghitung live pakai field yang sama dari npn.searchProduct (sudah sertakan decVolume & SAPdecUom).

## Peran ber-user tidak boleh dinonaktifkan
Jangan biarkan role dengan user assigned dinonaktifkan (is_active=false) — prepare lockout total karena getPermissions() di User.php memfilter roles.is_active. Guard ini di update(). Jika terlanjur nonaktif, aktifkan kembali via Role::where('id',49)->update(['is_active'=>true])."

## Trap duplikat materialisasi validasi SJ
Terdapat DUA jalur membuat receiving_items dari validasi SJ: SjValidationController::complete() auto-create Receiving+items, DAN ReceivingController::store() menyalin latestValidation COMPLETED. Guard "receiving berjalan" hanya cek PENDING/IN_PROGRESS — tidak mencegah double-materialize dari SJ yang sudah final. Saat mengubah alur, pastikan hanya satu jalur atau beri guard anti-duplikat.

## Kondisi receiving_items pakai vocab kanonik FISIK_*
Set kanonik condition: FISIK_BAGUS, FISIK_RUSAK, QTY_KURANG, ISI_KEMASAN_KURANG, EXPIRED_TIDAK_STANDAR, LAINNYA. Normalisasi di ReceivingItem::normalizeCondition() (map legacy GOOD/DAMAGED/MISSING/LESS/NOT GOOD). Wajib dipanggil di semua jalur tulis receiving_items: ReceivingItemController::store/update, ReceivingItemImport, dan ReceivingController::store/scanItem (validation scanItem menerima set kanonik + legacy). Jangan migrasi massal isi DB existing tanpa konfirmasi — UI/read side memetakan legacy via onezentra-web/src/lib/condition.ts.

## Jangan rujuk kolom rencana_kirim yang sudah di-drop
`rkh_number`, `no_dokumen`, `no_dokumen_date`, dan `dock_number` sudah di-drop dari `rencana_kirim` (lihat migration drop_unused_columns + rename no_dokumen→po_transporter). Jangan pakai kolom-kolom ini di where/orWhere maupun aturan validasi. Nomor RKH = `rkh_date`; No. Dokumen/SJ = `po_transporter`. Referensi ke kolom tak ada hanya error di MySQL (42S22) karena SQLite memperlakukan identifier tak dikenal sebagai string literal. `nextDockNumber()` sudah dihapus dari RencanaKirimController (query kolom drop) — jangan dihidupkan ulang.

## RencanaKirim: penulisan atomik & filter index
(1) store()/update() wajib membungkus header + items (delete-all lalu insert ulang) dalam DB::transaction — total_qty dan acuan validasi SJ tidak boleh tertinggal setengah ditulis. (2) index() mendukung filter `po_transporter` (exact, case-insensitive via whereRaw LOWER) dan `kode_depo` — ini yang dipanggil frontend sebagai early-warning duplikat PO; jangan dihapus, tanpa ini peringatan duplikat di form create mati total.

## Frontend kirim filter, backend harus benar-benar memakainya
Sebelum menambah query param baru di pemanggilan list (mis. `rencanaKirim.list({ po_transporter })`), pastikan index() controller memfilter param itu. Test sqlite tidak menangkap param yang diabaikan (query tetap sukses tanpa filter) — tambahkan test feature yang assert jumlah data terfilter, bukan cuma assertOk().
